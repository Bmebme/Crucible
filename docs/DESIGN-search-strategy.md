## 1. 定位与设计原则

### 1.1 搜索策略要解决的问题

Agent 在漏洞验证三步流程中提出性质完全不同的问题，搜索策略负责：

1. 判断问题的**认知类型**
2. 为每种类型配置**检索倾向**（全 / 准 / 可信 / 链）
3. 双引擎并行召回后的**合并方式**
4. 输出的**冲突与差异处理**

### 1.2 五条设计原则

| 原则 | 内容 |
|------|------|
| P1 倾向性由查询类型决定 | 不是所有问题都要"准"，也不是都要"全"——错配倾向 = 检索失败（见 §2） |
| P2 KB 枚举，Agent 选择 | 搜索输出候选与标注，不做行动决策（承接主方案 §6 第 5 条原则） |
| P3 LLM 只比对与呈现，不重写 | 合并层禁止改写机制事实——否则合并自身成为第三轮失真源 |
| P4 冲突不裁决 | 两库结论不一致时并列输出双方说法+证据，由 Agent/人裁决 |
| P5 合并发生在查询时 | 不建融合索引、不做离线对齐；差异与冲突是查询时的免费质检信号 |

## 2. 查询类型分类学（核心）

### 2.1 四种类型

| 类型 | 认知需求 | 典型问题 | 倾向性 | 核心指标 | 失败代价 |
|------|---------|---------|--------|---------|---------|
| **Q1 枚举型** | 穷尽列举 | 「有哪些文件处理组件？」「消息类型有哪些？」「这个模块暴露哪些接口？」 | **全** | **召回率**（枚举完整性） | 漏一个 = 漏一块攻击面 |
| **Q2 机制型** | 精确事实 | 「文件名如何进入 ImageMagick 命令？」「鉴权在哪一层做？」「参数如何处理？」 | **准** | **精确率**（结论正确率） | 错一个 = 整条路径错 |
| **Q3 经验型** | 历史实证 | 「这类场景以前怎么打的？」「哪个 payload 被 WAF 拦过？」 | **可信** | **采纳率**（经验命中率） | 过期结论 = 重复撞墙 |
| **Q4 链式型** | 多跳可达 | 「从上传接口能打到哪？」「逃逸失败还能做什么？」 | **链完整** | **中间点召回率**（无断链率） | 断一环 = 路径走不通 |

**核心指标定义**（倾向性与指标一一对应：要"全"就考核召回，要"准"就考核精确）：

| 类型 | 指标 | 定义 | 目标 |
|------|------|------|------|
| Q1 | 枚举完整性（召回率） | 检索返回的条目 ÷ 知识库中实际全部条目（人工清点对照） | > 95% |
| Q2 | 结论精确率 | 返回的机制结论中与事实一致的比例（冲突被检出并对峙输出不计为错） | 一致且正确 > 80% |
| Q3 | 经验采纳率 | 返回的历史记录中被 Agent 实际采纳的比例 | 持续观测，应随验证次数上升 |
| Q4 | 中间点召回率 | 候选路径覆盖真实路径全部中间机制点的比例 | > 90%（断链直接导致路径走不通） |

### 2.2 判别器

**关键词规则先行，LLM 兜底**（规则覆盖高频句式约七成，LLM 处理剩余与混合查询）：

| 规则信号 | 类型 |
|---------|------|
| 哪些 / 有哪些 / 类型 / 清单 / 列举 / 全部 | Q1 |
| 怎么 / 如何 / 调用 / 处理 / 版本 / 鉴权 / 实现 | Q2 |
| 以前 / 历史 / 验证过 / 被拦 / 结果 / 成功过 | Q3 |
| 路径 / 可达 / 从…到 / 能打到 / 还能做什么 | Q4 |

**LLM 判别 Prompt 骨架**（Haiku，一次调用，四分类 + 子查询拆分）：

```markdown
# 任务
将查询分为四类之一。分类依据是「答案需要什么」，不是问的主题。

# 类型定义（判别要点）
Q1 枚举型（全）：答案需要穷尽列举一组事物
   → 问「有哪些 / 全部 / 清单 / 类型」，要的是完整性
Q2 机制型（准）：答案需要精确描述机制事实
   → 问「怎么 / 如何 / 调用 / 版本 / 鉴权实现」，要的是准确性
Q3 经验型（可信）：答案需要历史实证
   → 问「以前 / 历史 / 被拦 / 验证过 / 结果」，要的是可信度
Q4 链式型（链）：答案需要多跳路径
   → 问「从…到… / 可达 / 能打到 / 还能做什么」，要的是链条完整

# 判别要点
1. 看疑问结构，不看领域词汇：「有哪些接口」≠「接口怎么做」
2. 混合查询 → 拆子查询，标出主类型
3. 输出 confidence；低于 0.7 标 ambiguous

# 示例
「这个产品有哪些文件处理组件？」→ Q1
「文件名是怎么进入 convert 命令的？」→ Q2
「上次 SSRF 验证是被什么拦的？」→ Q3
「从上传接口能打到内网 Redis 吗？」→ Q4

# 查询
{{query}}
```

**输出 schema**（判别结果 = 倾向性配置对象，不只是标签）：

```json
{
  "query_type": "Q2",
  "confidence": 0.9,
  "sub_queries": [
    {"type": "Q1", "text": "上传接口有哪些参数"},
    {"type": "Q2", "text": "文件名参数如何拼入命令"}
  ],
  "config": {"recall_mode": "precision", "merge_mode": "M2"}
}
```

**混合查询拆分规则**：Agent 的真实问题经常混合（「上传接口有哪些参数，文件名参数怎么处理？」）。主类型定主流程，`sub_queries` 并行触发各自类型的召回与合并模式，结果统一返回。子查询不重跑判别（类型已在拆分时确定）。

**低置信兜底**：`confidence < 0.7` → 标记 `ambiguous`，不二次猜测；走保守策略（四通道全召回，合并层按结果形态决定），或由 Agent 澄清。判别器遵循「判不准就不判」——与合并层的「冲突不裁决」同一哲学。

## 3. 总体架构

### 3.1 分层视图

![图9 融合检索架构](diagrams/fusion-search-architecture.svg)

```
query → ① 意图判别（类型 → 倾向性配置）
      → ② 双引擎并行召回（llm_wiki 页面引擎 / LightRAG 实体图引擎，各自原生）
      → ③ 三模式合并（按类型选择 M1~M4 之一）
      → ④ 输出：结果 + 溯源 + 冲突/差异标注
```

### 3.2 软件架构（组件 / 端口 / 存储）

![图10 软件架构](diagrams/search-software-architecture.svg)

组件职责：

| 组件 | 职责 | 关键约束 |
|------|------|---------|
| **融合检索网关**（FastAPI :19829） | 编排判别→召回→合并→回写全链路 | 不持有知识：两引擎各自存储与索引，网关只编排 |
| 判别器 | 查询类型分类（Q1~Q4）→ 倾向性配置 | 规则先行，Haiku 兜底 |
| 编排器 | 双引擎并行召回调度、按类型选通道、降级路径 | LightRAG 不可用时各模式自动降级 |
| 合并器 | 执行 M1~M4，LLM 比对与呈现 | 不重写、冲突不裁决、逐条引用 |
| 回写器 | 裁决结果回写、差异入 Lint 队列、状态流转与检索加权 | 回写后冲突消失（知识自愈） |
| llm_wiki 服务（:19828） | 页面检索/页面存储（wiki/ + frontmatter）/LanceDB 向量 | 不改内核 |
| LightRAG 服务 | local/global/mix 检索、实体图存储（Postgres/Neo4j）、LLM 抽取管线 | 定制实体/关系 schema |
| LLM 提供层 | Haiku（判别）· Sonnet/Opus（合并）· 抽取 LLM（LightRAG 摄入） | 按环节分模型，控制成本与质量 |

安全：全部组件仅绑定 127.0.0.1，token 认证与 llm_wiki 同模型。

## 4. 双引擎能力映射

| 维度 | llm_wiki（页面引擎） | LightRAG（实体图引擎） |
|------|---------------------|----------------------|
| 知识粒度 | 页面（叙述 + frontmatter 字段） | 实体 / 关系 / chunk |
| 检索能力 | 混合检索：关键词 + 向量 + 一跳 wikilink 图 | local（实体）/ global（社区多跳）/ mix / naive |
| 强项 | 清单页全量枚举、机制叙述、验证记录（状态字段） | 实体按类型全量枚举、关系多跳、跨页面关联 |
| 输出 | 页面内容 + 来源文档 | 实体 + 关系 + chunk 引用 |
| 与 K 分类的对应 | K1 场景 / K3 经验 / K2 叙述 | K2 实体化 / K4 目标-能力图 |

**互补关系**：枚举型问题两库都能答（需要并集）；机制型问题 wiki 给叙述、LightRAG 给关系（需要一致性比对）；链式问题 LightRAG 为主、wiki 补页面依据。

## 5. 核心：三倾向 × 四合并模式

### 5.0 检索策略流程总览

![图11 检索策略流程](diagrams/retrieval-strategy-flow.svg)

### 5.1 M1 并集合并 —— 服务于 Q1 枚举型（全）

**召回配置**：

- llm_wiki：关键词+向量检索清单类页面（组件清单/接口清单/消息类型页）
- LightRAG：按实体类型全量枚举（如 `service` 类型实体全量拉出）

**合并流程**（LLM 输入两库枚举结果，各带来源）：

```
输出 schema:
{
  "union":        ["ImageMagick", "FFmpeg", "Tika", "libreoffice"],   # 去重并集
  "differences": [
    {"item": "libreoffice", "only_in": "lightrag", "action": "回填 wiki 清单页"},
    {"item": "FFmpeg", "only_in": "wiki", "action": "检查 LightRAG 抽取为何遗漏"}
  ],
  "conflicts": [   # 同名不同描述
    {"item": "Tika", "wiki_says": "...", "rag_says": "...", "action": "待人工确认"}
  ]
}
```

**要点**：

- 不排序、不裁剪——枚举型问题的价值在完整性
- 差异清单是**免费失真检测**：两库独立提取，不一致处即可疑点
- 差异清单可直接作为**回填建议**（知识自愈）：only_in_rag → 补 wiki 清单页；only_in_wiki → 检查 RAG 抽取

### 5.2 M2 一致性合并 —— 服务于 Q2 机制型（准）

**召回配置**：

- llm_wiki：机制页 / 坑位级 surface 页（检索 + 读取）
- LightRAG：相关实体 + 关系（`injects`/调用关系 + chunk）

**合并流程**（LLM 输入双方结论**和各自证据**）：

```
输出 schema:
{
  "conclusion": "文件名以 shell 拼接方式进入 convert 命令",     # 仅当双方一致
  "confidence": "high",
  "evidence": [
    {"engine": "wiki", "claim": "shell 拼接调用", "source": "架构文档 §3.2"},
    {"engine": "lightrag", "claim": "filename → 命令行（injects）", "source": "接口规范 §5.1"}
  ]
}

# 冲突时输出：
{
  "conclusion": null,
  "conflict": {
    "wiki_says": {"claim": "...", "source": "..."},
    "rag_says":  {"claim": "...", "source": "..."}
  },
  "action": "不裁决，Agent / 人裁决后回写（§8）"
}
```

**要点**：

- **一致 → 高置信**：双证据互相印证
- **冲突 → 对峙输出**：不硬合并、不让 LLM 猜谁对——合并层不得制造第三轮失真（P3/P4）
- 每条 claim 必须带 source，无 source 的结论降级为 unverified

### 5.3 M3 状态排序 —— 服务于 Q3 经验型（可信）

**召回配置**：

- llm_wiki：verification/ 页 + poc/ 页，按 frontmatter 的 `verify_state` 过滤加权
- LightRAG：一般不参与（经验是页面形态）；若需按实体关联扩展，取一跳关系

**合并流程**：**不合并内容**——历史结果原样引用（哪个 payload 被拦、哪个绕过成功，一字不改），只做排序与标注：

| verify_state | 权重 | 处理 |
|-------------|------|------|
| verified_success | 1.0 | 置顶，标注验证时间与环境 |
| unverified | 0.5 | 标注「未经实测」 |
| verified_blocked | 0.2 | 仅当当前环境与记录环境匹配时作为**负知识**返回 |
| false_positive | 0 | 除非查询正是「为什么是误报」 |

**要点**：经验知识的内容是 Agent 行动的输入，LLM 合并（改写/综合）会破坏其可信度——原样引用 + 状态标注就是全部处理。

### 5.4 M4 路径合成 —— 服务于 Q4 链式型（链完整）

**召回配置**：

- LightRAG：global / mix 模式多跳查询（`reaches`/`trusts`/`injects` 链）
- llm_wiki：一跳 wikilink 扩展 + 相关机制页依据

**合并流程**：

```
输出 schema:
{
  "paths": [
    {
      "nodes": ["上传接口", "处理容器", "ImageMagick", "宿主机"],
      "hops": [
        {"from": "上传接口", "to": "处理容器", "relation": "reaches", "evidence": "架构文档 §3.1", "engine": "lightrag"},
        {"from": "处理容器", "to": "ImageMagick", "relation": "injects", "evidence": "接口规范 §5.1", "engine": "wiki+lightrag"}
      ]
    }, ...
  ],
  "notes": ["路径可行性未经实测，由 Agent 验证"]
}
```

**要点**：

- 每跳带关系类型 + 证据 + 来源引擎——Agent 决策时可见可信度
- 路径**可行性判断归 Agent**（KB 只合成候选链，不裁决）
- 两库链条不一致时：并列输出候选路径，不合并成一条"猜测路径"

## 6. 三步流程路由表

| Agent 步骤 | 主要查询类型 | 倾向性 | 合并模式 | 输出 |
|-----------|-------------|--------|---------|------|
| ① 场景构建 | Q1 枚举型 + Q3 案例 | 全 + 可信 | M1（攻击面/组件/消息类型）+ M3（历史案例） | 并集清单 + 差异标注 + 案例（状态排序） |
| ② 路径规划 | Q2 机制型 + Q4 链式型 | 准 + 链完整 | M2（机制事实）+ M4（路径候选） | 一致性结论 + 候选路径（每跳依据） |
| ③ POC 生成与验证 | Q3 经验型 + Q2 机制型 | 可信 + 准 | M3（历史 POC 与结果）+ M2（契约细节） | 原样历史记录 + 一致性契约结论 |
| 验证后回写 | — | — | —（M 之外） | 结果 → 状态流转 → 检索加权（§8） |

## 7. LLM 合并 Prompt 契约

### 7.1 四个统一约束（所有模式共用）

```
1. 你是比对器与呈现器，不是生成器：不得改写、综合、推测输入中未出现的机制事实
2. 每条输出必须引用来源（engine + source）；无来源的内容标注 unknown
3. 两库结论冲突时：并列输出双方说法与证据，禁止裁决、禁止折中
4. 输出严格遵循给定 JSON schema，多余内容放在 notes 字段
```

### 7.2 模型分工

| 环节 | 模型 | 理由 |
|------|------|------|
| 意图判别 | Haiku | 四分类，低成本高并发 |
| M1 并集合并 | Haiku 或 Sonnet | 去重比对为主，推理负担轻 |
| M2 一致性合并 | Sonnet/Opus | 需要严格循证比对，错误代价高 |
| M3 状态排序 | 无需 LLM | 字段过滤与加权是确定性操作 |
| M4 路径合成 | Sonnet | 多段证据对齐 |

### 7.3 提示词骨架（M2 示例）

```markdown
# 角色
你是漏洞验证知识库的合并器。输入是 llm_wiki 与 LightRAG 两个引擎对同一机制问题的检索结论。

# 输入
## llm_wiki 结论
{{wiki_claim}}（来源：{{wiki_source}}）
## LightRAG 结论
{{rag_claim}}（来源：{{rag_source}}）

# 任务
判断两库结论是否指向同一事实。
- 一致：输出合并结论 + evidence 数组（双方各一条）
- 冲突：conclusion 置 null，conflict 对象并列双方说法与证据

# 约束
不得改写、综合、推测输入之外的机制事实。不得在冲突时选择其中一方。
按 JSON schema 输出。
```

## 8. 失真与质量控制

### 8.1 搜索策略自身的失真防护

| 风险 | 防护 |
|------|------|
| LLM 合并时改写机制事实（第三轮失真） | P3：只比对呈现；约束 1 写入所有 prompt |
| LLM 合并时裁决冲突（猜错） | P4：冲突对峙输出，选择权在 Agent/人 |
| 枚举遗漏 | M1 双引擎并集 + 差异清单提示回填 |
| 经验知识被综合改写 | M3 原样引用，不经过 LLM 内容变换 |

### 8.2 裁决结果的回写闭环

冲突与差异的裁决结果**必须回写**，否则同样的冲突反复出现：

- 人工裁决「wiki 对」→ 修正 LightRAG 实体/关系（`insert_custom_kg` 或重抽取该 chunk）
- 人工裁决「RAG 对」→ 修正 wiki 页面叙述
- 差异确认「两边都对（不同维度）」→ 两边各补交叉引用

回写后冲突消失——**知识库在检索中自愈**，这是静态方案没有的维护机制。

### 8.3 评估指标

四类核心指标与 §2.1 对齐，另加合并层专项指标：

| 指标 | 定义 | 目标 |
|------|------|------|
| 枚举完整性（Q1 召回率） | M1 并集覆盖人工清点的比例 | > 95% |
| 结论精确率（Q2 精确率） | M2 返回的机制结论与事实一致的比例 | > 80% |
| 机制一致率 | M2 中双库一致且正确的比例 | 一致且正确 > 80% |
| 冲突检出收益 | 冲突中确有一方错误的占比（检出了真问题） | > 50% |
| 经验采纳率（Q3） | M3 返回的历史记录中被 Agent 采纳的比例 | 随验证次数上升 |
| 中间点召回率（Q4） | M4 候选路径覆盖真实路径全部中间机制点的比例 | > 90% |
| 路径有效率 | M4 候选路径被采纳且走通的比例 | — |

## 9. 实现要点

1. **查询时融合**：无融合索引、无离线对齐；判别与合并都在查询路径上（P5）
2. **服务形态**：薄网关（或直接实现为 MCP 工具 `kb_search` 内部逻辑），编排两引擎 API 调用
3. **降级路径**：LightRAG 不可用时，M1 退化为 wiki 单源枚举、M4 退化为 wikilink 一跳扩展；M2 退化为单源结论（confidence 降级）
4. **缓存**：同 query 短时缓存合并结果；差异清单与冲突报告持久化到 wiki 的 Lint 队列
5. **先跑通 M1 + M3**（枚举与经验是最高频），再上 M2/M4（需要更多 prompt 打磨）
