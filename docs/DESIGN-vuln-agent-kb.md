## 1. 背景与定位

### 1.1 消费者：漏洞验证 Agent

针对特定产品、**目标驱动**的攻击验证 Agent：

```
外层循环（目标管理）: 明确目标 → 了解产品内部机制 → 从起点出发 → 利用中动态调整目标
内层流水线:        ① 攻击场景构建 → ② 攻击路径规划 → ③ POC 生成 + 实际环境验证
```

典型流程（容器逃逸）：先明确「获取宿主机权限」这一目标，了解容器与宿主机制后从某个起点开始利用；若逃逸不可行，按降级链动态切换为容器内横向、敏感数据读取等替代目标。目标管理消费 K4 威胁知识，三步流水线消费 K1~K3（§2、§3）。

### 1.2 知识库的角色定位

不是「回答问题的助手」，而是「为攻击行动提供弹药和地图的作战参谋」：

| 角色 | 对应能力 |
|------|---------|
| **罗盘** | 提供目标坐标系——目标层级、目标间关系（requires/grants/降级）、历史走通状态（K4）；选哪个目标由 Agent 决策 |
| **场景库** | 提供「这个产品上可以打什么」——产品场景、漏洞模式、历史案例 |
| **地图** | 提供「从哪里走到哪里」——实体关系图上的多跳路径 |
| **弹药库** | 提供「具体怎么打」——实现细节、接口契约、POC 剧本 |
| **记忆** | 提供「上次打的结果如何」——验证日志、拦截特征、误报记录 |

这四重角色中，**「记忆」是传统知识库完全没有的维度**，也是本方案区别于所有通用问答/RAG 方案的根本（§5）。

### 1.3 为什么是「轻知识库 + 重 Agent」

1. **路径组织、目标选择、POC 组装是 Agent/skill 的能力**，不是知识库的职责（§3）。KB 收缩为「知识点供给器」：输出威胁、关键机制、场景、经验等知识点；Agent 基于知识点自行组织攻击路径。
2. 因此 **v1 单引擎 llm_wiki** 即可：wiki 页面 = 知识点（wikilink 提供导航），混合检索 = 召回。hieraextract 的输出退化为启动期种子（§11）。
3. **LightRAG 实体图降级为可选召回增强**（§7.3）：仅当知识点增多后出现多跳召回瓶颈（入口与 sink 之间的中间机制点漏召回）时引入，用于提升召回，不承担路径组织。
4. 验证闭环沉淀大量经验性叙述——这是 llm_wiki「持续演化 wiki」的强项，也是复利层（K3b）的载体。

## 2. 知识分类学：我们需要什么知识（先于架构）

### 2.0 核心命题：知识形态由消费动作决定

- 普通问答的消费动作是**生成回答** → 知识是描述性的（是什么、包含哪些模块）
- 漏洞验证的消费动作是**规划并执行攻击** → 知识必须是可行动性的（怎么走、哪里有坑、怎么验证）

由此得到四类知识：

| 类别 | 一句话定义 | 对应你的表述 |
|------|-----------|-------------|
| **K1 场景知识** | 用户/外部行为穿过产品的完整路径，含数据流与信任变化 | 我们产品里的场景 |
| **K2 实现知识** | 安全相关粒度上的实现真相（坑位级） | 产品的详细知识实现 |
| **K3 专家经验** | 模式/案例/绕过等先验 + 本产品实测记忆 | 我们的专家经验 |
| **K4 威胁知识** | 攻击者目标层级、所需/解锁能力、失败时的降级目标 | 威胁（Agent 的目标坐标系） |

### 2.1 K1 场景知识（产品里的场景）

**定义**：不是「产品有哪些模块」，而是「用户的一个动作经过哪些组件、数据怎么流、权限怎么变」。

每个场景必须刻画五个要素：

| 要素 | 含义 |
|------|------|
| 入口 entry | 谁发起、从哪个边界进入 |
| 组件链 path | 经过哪些组件/服务，按顺序 |
| 数据流 data_flow | 哪些数据经过、落点在哪里 |
| 信任变化 trust_transitions | 哪些位置信任升级/降级 |
| 状态机 states | 哪些状态可被外部操纵 |

**示例 —— 场景「用户上传头像」**：

```
入口:     登录用户 → POST /api/upload（外部边界）
组件链:   上传接口 → 对象存储 → 图片处理服务 (ImageMagick) → CDN 分发
数据流:   用户文件 → 服务器处理链 → 公开可访问的 CDN 地址
信任变化: 不可信用户文件 → 进入服务器端图像处理命令
状态机:   上传中 / 处理中 / 失败 / 已发布（文件名可控，状态可被重复触发）
```

场景库按业务域组织：登录会话类 / 上传文件类 / 订单支付类 / 管理操作类 / 第三方集成类。

### 2.2 K2 实现知识（产品的详细知识实现）

**定义**：普通问答到「订单模块负责订单管理」就停；漏洞验证要到「这个参数在哪一行拼进了什么」。

粒度对比（同一产品、同一模块）：

| 粒度 | 普通知识 | 实现知识（坑位级） |
|------|---------|-------------------|
| 技术栈 | 用了 Java | spring-boot **2.3.1** + MyBatis 3.5.3 + fastjson **1.2.66** |
| 接口 | 有订单查询接口 | `/api/order/query` POST，参数 orderId **无白名单校验**，鉴权仅登录态，**错误信息回显 SQL 片段** |
| 数据 | 数据存在订单库 | orderId **字符串拼接进 SQL**（Mapper XML `${orderId}`），落 MySQL 5.7 |
| 部署 | 集群部署 | 入口 Nginx（**无 WAF 规则覆盖该路径**）→ 服务 10.0.1.x → **内网 Redis 无密码** |
| 依赖 | 用了图像处理库 | ImageMagick **6.9.2**（受 CVE-2016-3714 影响），调用方式为 **shell 拼接 exec** |

来源：API 规范、源代码、配置文件、部署拓扑、依赖清单（SBOM）。

**机制点定级标准（三问）**：每个机制点必须能回答三个问题，否则只是结构描述，不构成机制点：

1. **怎么通信**（通信机制）：协议、调用方式、数据流向
2. **有什么安全机制**：鉴权、输入校验、防护措施、加密
3. **面对哪些威胁**：该机制缺失或失效时对应的风险（可关联 K4 威胁点）

示例：机制点「处理容器」——① 通信：上传接口 HTTP POST → 容器内 exec 调用 ② 安全机制：无（shell 拼接、无文件类型校验）③ 威胁：命令执行 / 容器逃逸。

**与 K1 的关系**：K1 说「文件进入图片处理服务」，K2 说「处理服务的 convert 版本是 6.9.2 且用 shell 拼接调用」。场景提供"走到哪"，实现提供"哪里有坑"。

### 2.3 K3 专家经验

分两类，性质不同：

| 子类 | 内容 | 性质 |
|------|------|------|
| **K3a 外部经验** | 漏洞模式库（55+ 类型，带前提条件 + 探测方法）、历史案例（WooYun 88,636 + 内部审计发现）、绕过技术（WAF 绕过/编码/协议特性）、验证方法论（PoC 设计/判定准则） | 先验：「这类产品一般会这样」 |
| **K3b 内部记忆** | 本产品实测过的验证：成功路径、拦截特征、误报记录、环境差异 | 实证：「这个产品实测就是这样」 |

K3b 随验证次数增长（§9 闭环），是知识库的复利层——先验经验人人可查，实证记忆只有我们自己的知识库有。

### 2.4 K4 威胁知识（目标层级 + 降级链）

**定义**：攻击者「想要什么、需要什么、拿不到时退而求什么」的知识。Agent 是目标驱动的，K4 就是它的目标坐标系。

三个组成：

**① 目标层级（Goal Hierarchy）**

| 层级 | 内容 | 示例 |
|------|------|------|
| 终极目标 | 攻击的最终诉求 | 数据窃取、业务破坏、勒索、供应链污染 |
| 能力目标 | 通往终极目标的关键能力 | 宿主机权限、横向移动、提权、持久化 |
| 中间目标 | 达成能力目标的技术里程碑 | 命令执行、任意文件读、SSRF、凭据获取 |

**② 能力映射** — 每个目标标注两个能力集，构成「目标-能力图」：

- `requires`（所需能力）：达成该目标需要已具备什么（前置条件）
- `grants`（解锁能力）：达成该目标后新获得什么（开启哪些新目标）

**③ 降级链（Fallback Chain）** — 每个目标标注失败时的替代目标。这是「动态调整目标」的知识基础：

![图8 目标层级与降级链（容器逃逸示例）](diagrams/goal-lattice.svg)

Agent 的消费方式：利用过程中以当前能力集查询可达目标——「我现在有容器内执行能力，逃逸不可行，还能做什么？」这类查询基于 threat/ 页的结构字段（降级链列表 + 能力标注）做**枚举**——输出候选集，选择归 Agent。这也是 K4 与普通问答知识最本质的区别：**普通问答没有「目标」这个概念，K4 把目标做成了一等实体。**

### 2.5 与普通问答知识的五维对比

| 维度 | 普通问答知识 | 漏洞验证知识 |
|------|-------------|-------------|
| **组织维度** | 结构盘点（包含哪些模块） | 场景 + 机制 + 威胁（行为穿过什么 · 通信与安全机制是什么 · 面对哪些威胁） |
| **描述深度** | 职责级（模块负责什么） | 坑位级（参数在哪拼接、版本是什么、怎么调用的） |
| **时间性** | 中性百科（通用成立） | 前提化（版本/鉴权态/可达性下成立） |
| **消费方式** | 阅读后生成回答 | 消费后生成动作（探测/路径/POC） |
| **演化** | 静态 | 实测审判 + 经验复利 |
| **目标维度** | 无（知识不关联目标） | 目标层级 + 能力映射 + 降级链（K4） |

### 2.6 聚焦原则：可达性过滤

安全知识「非常聚焦」不是口号，是四条可执行的过滤规则：

1. **可达性过滤** — 只保留从攻击面（外部/低权限可达）出发能触及的知识；纯内部管理模块的文档细节不进入场景库
2. **坑位粒度** — 实现知识只到安全相关粒度：参数处理方式、精确版本、调用方式；业务无关代码细节不进入
3. **前提过滤** — 经验必须带适用前提，不带前提的漏洞模式是噪声
4. **产品过滤** — 只保留本产品技术栈适用的模式/案例；Java/Spring 产品的 .NET 案例优先级最低

### 2.7 综合示例：一个场景，四类知识协同

以「用户上传头像 → 服务器命令执行」为例：

```
K1 场景: 上传入口 → 图片处理链 → 信任变化位置（文件进入服务端处理命令）
K2 实现: ImageMagick 6.9.2，shell 拼接调用，文件名可控
K3a 经验: ImageTragick (CVE-2016-3714)，前提 convert < 6.9.3-9，探测：mvg payload
K3b 记忆: 上次验证 mvg 后缀被 WAF 拦 → 换 msl 内容类型绕过成功 → verified_success
K4 威胁: 目标「服务器命令执行」，若失败按降级链切换为「敏感文件读取 / SSRF 内网探测」
```

Agent 三步的消费路径：

```
① 场景构建: K1 找到「上传场景」+ K3a 匹配「文件处理类模式」
② 路径规划: K1 组件链 + K2 部署事实 → 多跳路径
③ POC 生成: K2 接口契约 + K3a 探测方法 + K3b 绕过记忆
④ 结果评估: 失败 → K4 降级链切换目标；成功 → K3b 回写记忆
```

### 2.8 四类知识的落位（映射到存储）

| 知识 | wiki 侧（叙述层） | RAG 图侧（实体层） |
|------|------------------|-------------------|
| K1 场景 | `scenario/` 页（五要素结构化进 frontmatter） | 场景-组件-资产实体链 |
| K2 实现 | `surface/` + `knowledge/` 页（坑位级字段） | `endpoint`/`param`/`service` 实体 + `injects`/`reaches` 边 |
| K3a 经验 | `pattern/` + `case/` 页 | `vuln_pattern` 实体 + `affected_by` 边 |
| K3b 记忆 | `verification/` 页 + 状态机字段 | `mitigated_by` 边（拦截事实）+ 新发现边 |
| K4 威胁 | `threat/` 页（目标层级 + 降级链，结构进 frontmatter） | v1：页内结构字段；（可选）`goal`/`capability` 实体 + `grants`/`alternative_to` 边 |

## 3. Agent 流程的知识需求分析

### 3.1 外层循环：目标管理（消费 K4）

```
明确目标（K4 目标层级）→ 执行三步流水线 → 评估验证结果 → 动态调整目标（K4 降级链）→ 循环
```

目标管理是 Agent 的驱动轴：起点确定后先定目标；验证中若目标不可行（逃逸失败/被阻断），按降级链切换到替代目标继续，而不是终止。

### 3.2 内层流水线：三步与四类知识的对应

| 步骤 | 本质 | 消费的知识 | 检索特征 |
|------|------|-----------|---------|
| ① 攻击场景构建 | **发散**：给定产品与目标，枚举可能攻击 | K1 场景 + K3a 模式/案例 + K4 目标-场景匹配 | 模式匹配、按技术栈/组件过滤、前提校验 |
| ② 攻击路径规划 | **收敛**：给定入口与目标，规划路径 | KB 仅召回两类点——机制点（K2 通信/安全机制）与历史问题（K3b）；**路径组织由 Agent 完成**（拿点 → 看关联 → 再取点）；证据由第③步实测验证得出，不在本步提供 | 知识点召回；多跳关联靠 Agent 迭代 |
| ③ POC 生成+实测 | **执行**：写出并运行验证 | K2 接口契约 + K3a 探测方法 + K3b 验证记忆 | 精确命中、版本过滤、经验复用 |
| ④ 结果评估→目标调整 | **决策**：成败后往哪走 | K4 降级链 + K3b 历史结果 | 目标-能力图查询（`grants`/`alternative_to` 遍历） |

## 4. 知识库的特征特点与作用

### F1 可执行性（Executable Knowledge）

每条知识携带机器可消费的结构，而不只是叙述：

- 攻击场景页带 `steps` 数组（每步含工具调用参数）
- 契约页带结构化请求模板（method/path/params/auth）
- POC 剧本带占位符模板 + 验证断言

Agent 的 tool-calling 能直接消费这些字段，无需二次解析叙述文本。

### F2 条件化（Conditional Knowledge）

每条知识标注**适用前提**，检索时按前提过滤：

```yaml
preconditions:
  - version: "< 2.3.1"          # 版本条件
  - auth: "user_login"           # 鉴权态条件
  - reachable_from: "external"   # 可达性条件
```

漏洞知识离开前提就是废话——「该参数存在注入」只有在「哪个版本、什么鉴权态、从哪里可达」的条件下才可执行。

### F3 攻击视角组织（Attack-Oriented Organization）

知识按**攻击面的维度**组织，而非文档结构：

```
文档结构:   产品手册 → 第3章 → 订单模块 → 接口说明
攻击视角:   外部可达 → 未鉴权接口 → 订单查询(参数orderId) → 注入点候选
```

同一份原文，组织维度从「作者怎么写的」变成「攻击者怎么找的」。

### F4 多跳关系（Multi-Hop Relations）

支持路径检索而非段落检索：实体关系类型为攻击语义定制（`reaches`/`trusts`/`injects`/`affected_by`，见 §7.3），查询「从登录接口到订单库有多少条路径」是图操作，不是关键词匹配。

### F5 验证状态机（Verification State）

每条攻击知识有验证状态，决定检索权重（§9）：

```
unverified（LLM 断言） → verified_success（实测成功，boost）
                        → verified_blocked（被拦截，降权 + 环境标注）
                        → false_positive（误报，修正模式前提）
```

### F6 失败知识入库（Negative Knowledge）

被 WAF 拦截的特征、补丁版本、环境差异、误报原因**全部入库**。对验证 Agent 而言，「这条路走不通」和「这条路走得通」价值相同——前者防止重复撞墙，后者加速复现。

### F7 经验复利（Compounding Experience）

每次验证都回写知识库（K3b）：新的成功案例、新的拦截特征、新的环境事实。知识库随攻击次数增长而**越来越准**——这是 llm_wiki「知识编译一次、持续维护」理念在攻击领域的直接应用，也是任何静态 RAG 做不到的。

### F8 分级与安全（Tiering）

POC 剧本、验证凭据、未修复漏洞细节按敏感度分级存储与检索（§13），防止知识库本身成为泄露面。

**作用总结**：给场景构建发散的素材、给路径规划收敛的地图、给 POC 生成精确的弹药、给未来攻击累积的记忆。

## 5. 倾向性知识设计 —— 与传统问答/MCP 的差异化

传统问答（普通 RAG）和传统 MCP 的共同假设是：**知识是中性的，检索是问题驱动的，输出是文本**。本方案对这三条假设逐一反转（承接 §2 的分类学）。

### 5.0 差异化的诚实边界

先划掉站不住脚的差异：**话题覆盖不是差异**——漏洞案例、模式描述、公开 POC，传统问答知识库（段落检索 / 图增强检索 / 知识 Wiki）只要索引了对应文档就查得到。

真正站得住的三点差异：

1. **回答的问题不同** — 传统库回答「产品包含哪些模块」（结构盘点）；本方案回答「模块有哪些通信与安全机制、面对哪些威胁」（攻击语义，§2.2 三问）
2. **知识形态不同** — 传统库返回段落（案例文本、模式描述），Agent 使用前必须自行**二次提炼**前提与探测——又一轮 LLM 转化，必然再叠一层失真；本方案返回**字段化的知识点**（前提 / 探测 / 验证状态），提炼在入库时一次性完成（专家预编译 + 人工审核 + 实测修正），Agent 直接消费字段，跳过二次提炼
3. **实验反馈源** — 唯一结构性缺失项：传统库从文档演化，没有实测反馈；本方案有验证状态机（§5.4）与负知识（§5.5）

### 5.1 面向利用，而非面向描述（K2 知识形态）

| 传统知识 | 攻击倾向知识 |
|---------|-------------|
| 「订单查询接口接收 JSON 参数 orderId，返回订单详情」 | 「订单查询接口：JSON 参数 orderId，无额外鉴权校验，参数拼接进入 SQL（**可达注入点**），**前提**：登录态 + 商品存在；**探测方法**：注入 `' OR 1=1 --` 观察差异；**验证状态**：unverified」 |

区别：传统知识回答「这是什么」，倾向知识回答「**这能怎么被利用、在什么条件下、怎么验证**」。每一个知识点都带有利用维度的标注（可达性、前提、探测方法、状态）。

### 5.2 场景驱动检索，而非问题驱动

- 传统：用户问「X 是什么」→ 检索 X → 回答
- 本方案：Agent 提交**场景上下文** `{入口点, 已具备能力, 目标资产, 产品版本}` → 检索返回**候选攻击场景**（按匹配度排序），而非段落

检索接口的第一参数不是 query 字符串，而是场景描述对象。`kb_scenario` 工具接受的输入示例：

```json
{
  "context": {
    "entry": "外部未鉴权的文件上传接口",
    "goal": "获取服务器命令执行权限",
    "stack": {"language": "java", "framework": "spring-boot 2.x"},
    "product_version": "3.1.0"
  }
}
```

### 5.3 输出可执行工件，而非段落

MCP 工具返回结构化工件，Agent 直接消费：

```
kb_scenario → AttackScenario { title, preconditions, steps[], expected_result, rollback }
kb_path     → PathPlan { nodes[{id,kind,evidence}], edges[{rel_type,confidence}], estimated_risk }
kb_poc      → POCSkeleton { template, placeholders, assertions, env_refs[] }
```

传统问答的最终产物是「一段话」；本方案的最终产物是「**下一步动作清单**」。LLM 只负责把工件实例化（填占位符），不再负责从段落里重新推导。

### 5.4 验证状态闭环：实测由 Agent 执行，状态由知识库维护（K3b 的生成机制）

传统知识库是静态的——LLM 说「可能存在 SSRF」，它就永远是「可能存在」。本方案里这是**假设（unverified）**。实测验证由 Agent 在真实环境执行；知识库只负责**接收验证结果 → 状态流转 → 检索加权**：

- 验证成功 → `verified_success`，检索 boost，沉淀为可复用模板
- 被拦截 → `verified_blocked`，记录拦截特征（WAF 规则、补丁版本），未来检索中作为**负知识**返回
- 误报 → `false_positive`，修正该漏洞模式的前提条件（如「该 SSRF 模式需服务端支持 gopher 协议」，本产品不支持 → 前提收窄）

结果是：知识库里的知识**越来越接近事实**，而不是越来越接近「LLM 觉得的事实」。这是对抗 LLM 失真的终极手段——用真实环境的结果覆盖模型断言。

### 5.5 失败知识是一等公民

| 传统方案 | 本方案 |
|---------|--------|
| 只保存「正确」的知识，失败尝试丢弃 | 失败验证 → 负知识页（拦截特征/环境差异/失败原因），检索时与正知识一起返回 |
| 新 Agent 每次重新撞同一堵墙 | 新场景构建时直接排除已验证 blocked 的路径，或在检测到环境变更时提示重验 |

### 5.6 路径优先于段落

传统 RAG：top-k 相似段落 → LLM 拼答案。本方案：检索的一等产出是**带关联标注的知识点集**（机制点 + 威胁点 + wikilink 一跳关联 + 溯源）；多跳路径由 Agent 从知识点迭代组装（拿点 → 看关联 → 再取点），段落退居为知识点的证据。**KB 不做路径组织——那是 Agent 的推理，不是检索的职责。**

### 5.7 与工具链耦合的操作知识

知识直接引用 Agent 的工具与动作，形成「知识 → 动作」直通：

```yaml
# 场景页 steps 片段
steps:
  - tool: http_request
    params: {method: POST, path: "/api/order/query", body_template: "..."}
  - tool: observe
    note: "对比注入前后响应差异，差异即注入证据"
```

传统 MCP 是「工具 + 模型判断」（无先验知识）；本方案是「**工具 + 先验操作知识 + 模型判断**」——模型不再从零发明步骤，而是实例化已验证的步骤模板。

### 5.8 版本与环境敏感

攻击知识按产品版本分叉（v3.0 的注入点在 v3.1 可能已修复），检索携带版本过滤器。传统问答库不做版本维度，回答天然过期。

### 5.9 目标导向：降级链检索

传统问答只服务「回答问题」，本方案还要服务「**换一个问题**」——当目标不可行时，Agent 需要的不是更长的解释，而是降级链：

```
「逃逸被阻断」→ kb_goal 查询 → 替代目标列表（容器内横向 / 敏感数据读取 / 持久化）
  → 每个替代目标附带：所需能力（是否已具备）、预期收益、验证方法
```

这是目标-能力图上的图查询（§2.4），检索产出是「**下一步可选什么**」（候选集 + 关系 + 历史状态），「选哪个」由 Agent 按任务上下文决策——**KB 枚举，Agent 选择**。

## 6. 总体架构

![图6 漏洞验证 Agent 知识库架构](diagrams/vuln-agent-architecture.svg)

四条设计原则：

1. **双引擎独立摄入、互不依赖** — 没有对齐层、没有融合图、没有事件联动。llm_wiki 与 LightRAG 各自从同一语料独立提取，天然形成交叉验证（矛盾时提示用户，白捡失真检测）。
2. **MCP 是唯一出口** — Agent 只通过 MCP 工具面接触知识，工具语义按 Agent 步骤设计（§8.2），而非按底层引擎设计。
3. **验证结果必须回写** — 验证是知识生命周期的一部分，不是知识库之外的动作（§9）。
4. **失败与成功同等入库** — 负知识是验证 Agent 的核心资产之一。
5. **知识-决策边界** — KB 承载目标空间的结构与事实（枚举候选 + 关系 + 历史状态），Agent 承载选择与权衡（任务价值/成本/风险）。KB 永远不替 Agent 做决策。

## 7. 数据模型设计

### 7.1 wiki 页面类型分类法（llm_wiki 侧）

| 目录 | 内容 | 承载知识 | 对应 Agent 步骤 |
|------|------|---------|:---:|
| `wiki/scenario/` | 攻击场景模板（五要素 + 步骤 + 预期） | K1 | ① |
| `wiki/surface/` | 攻击面页（端点/输入/协议，坑位级） | K2 | ①② |
| `wiki/knowledge/` | 产品实现知识（技术栈/依赖/部署事实） | K2 | ①② |
| `wiki/pattern/` | 漏洞模式（前提条件 + 探测方法） | K3a | ① |
| `wiki/case/` | 历史案例（WooYun、同类产品、内部发现） | K3a | ① |
| `wiki/poc/` | POC 剧本（占位符模板 + 断言） | K3a 固化 | ③ |
| `wiki/verification/` | 验证日志（每次实测的完整记录） | K3b | ③→回写 |
| `wiki/threat/` | 目标层级 + 降级链（结构进 frontmatter） | K4 | 目标管理 |

### 7.2 页面 frontmatter 扩展

```yaml
---
kb_type: scenario            # scenario/surface/knowledge/pattern/case/poc/verification
target_step: 1               # 服务于 Agent 第几步
preconditions:               # F2 条件化
  - version: "< 2.3.1"
  - auth: "user_login"
verify_state: verified_success   # unverified/verified_success/verified_blocked/false_positive
verify_date: 2026-08-20
verify_env: "staging-3.1.0"
tools_used: [http_request, sql_client]   # F7 操作知识
sensitive: false             # F8 分级
source_documents: [docs/api-spec.pdf]
---
```

### 7.3 LightRAG 实体/关系类型（可选召回增强，v1 不启用）

**定位**：不承担路径组织（§3），只解决「知识点增多后的多跳召回」问题。v1 纯 llm_wiki 起步；当入口与 sink 之间的中间机制点出现漏召回时再引入。若引入，实体类型如下（提取 prompt 中定制）：

| 实体类型 | 含义 | 示例 |
|---------|------|------|
| `endpoint` | 接口端点 | `/api/order/query` |
| `param` | 参数/输入 | `orderId` |
| `service` | 服务/组件 | 订单服务、Redis、ImageMagick |
| `vuln_pattern` | 漏洞模式 | SQLi、SSRF |
| `asset` | 关键资产 | 订单库、支付密钥 |
| `mitigation` | 防护措施 | WAF、参数化查询 |
| `goal` | 攻击目标 | 宿主机权限、数据窃取 |
| `capability` | 攻击能力 | 容器内命令执行、内网可达 |
| `technique` | 攻击技术 | 容器逃逸、挂载卷读取 |

关系类型（路径规划的关键）：

| 关系 | 语义 | 用途 |
|------|------|------|
| `reaches` | A 可达 B（网络/调用可达） | 路径可达性 |
| `trusts` | A 信任 B 的输入 | 信任边界穿越 |
| `injects` | A 参数进入 B 的上下文（SQL/命令/模板） | 注入点定位 |
| `affected_by` | A 资产受 B 漏洞模式影响 | 场景-资产匹配 |
| `mitigated_by` | A 被 B 防护 | 排除路径/记录拦截（K3b 落图） |
| `grants` | 达成 A 后解锁能力 B | 目标-能力图（K4） |
| `requires` | A 需要能力 B 为前提 | 目标前置条件（K4） |
| `alternative_to` | A 不可行时的替代目标 B | 降级链（K4） |

多跳查询示例：「入口 `endpoint:/upload` → 能 `reaches` 哪些 `service` → 其中哪些 `injects` 到 `asset:订单库`」——三步路径即攻击路径的骨架。

## 8. 检索设计：按 Agent 步骤路由

### 8.1 路由表

| Agent 步骤 | 检索意图 | 主通道 | 输出工件 |
|-----------|---------|--------|---------|
| 目标设定/调整 | 降级链枚举（K4） | threat/ 页检索 + 页内结构字段展开（v1）；可选 LightRAG 查询 | `GoalPlan[]`（目标+能力缺口+降级备选） |
| ① 场景构建 | 场景-模式匹配（K1+K3a+K4） | llm_wiki 混合检索（pattern/scenario/case/threat 页） | `AttackScenario[]` + 相关威胁/机制点 |
| ② 路径规划 | **Agent 内部推理**（KB 不做路径组织） | KB 仅提供机制点召回（llm_wiki 混合检索 + wikilink 一跳关联） | 机制点集（Agent 自行组装路径） |
| ③ POC 生成 | 精确契约+经验（K2+K3a+K3b） | llm_wiki token 检索（surface/poc 页）+ `verification/` 同场景历史结果 | `POCSkeleton` + 历史结果 |
| ④ 结果评估→目标调整 | 降级链枚举（K4+K3b） | threat/ 页降级链字段 + `verification/` 历史 | 候选替代目标（Agent 选择） |
| 回写 | — | `kb_record_verification` → 状态流转 + 经验页 + 图边增补 | — |

### 8.2 MCP 工具面

| 工具 | 输入 | 输出 | 服务步骤 |
|------|------|------|:---:|
| `kb_goal` | 当前能力集 + 期望目标 | 目标层级定位 + 能力缺口 + 降级备选（§2.4） | 目标管理 |
| `kb_scenario` | 场景上下文对象（§5.2） | 候选攻击场景 + 相关威胁/机制点（含前提过滤） | ① |
| `kb_poc` | 场景 + 目标端点 | POC 骨架 + 占位符 + 历史验证结果 | ③ |
| `kb_record_verification` | 验证结果（成功/拦截/误报 + 环境） | 状态流转 + 回写确认 | 闭环 |
| `kb_search` | 自由文本 | 混合检索（兜底） | 任意 |

工具面与 LightRAG MCP 的既有工具（`query_text` 模式、`get_knowledge_graph`）同构，迁移成本低；差异在语义：**我们的工具按 Agent 步骤命名和切片，返回工件而非段落**。

## 9. 验证反馈闭环

![图7 知识验证状态机](diagrams/verification-state.svg)

分工：**实测执行与结果判定是 Agent 的事；知识库只做接收回写、状态流转与检索加权。**

回写动作（Agent 提交验证结果后，KB 执行）：

1. **成功** → 页面 `verify_state: verified_success` → 检索加权；将本次成功路径/参数固化为模板
2. **拦截** → `verified_blocked` → 新增/更新负知识页（拦截特征：WAF 规则、补丁版本、环境差异）
3. **误报** → `false_positive` → 修正对应 `pattern/` 页的前提条件
4. 所有结果 → `verification/` 新页 + `log.md` 条目（可 grep 审计）
5. 新发现的机制事实 → 回写为页面字段/wikilink（如「该端点实测可达内网 Redis」→ 对应 surface/ 页新增关联段落）

闭环收益：Agent 第二次面对同一产品时，检索结果已被上一次实测**重新排序和过滤**——这是静态方案无法获得的复利。

## 10. 与传统方案对比

| 维度 | 传统问答知识库（RAG / 图增强 / Wiki） | 传统 MCP（纯工具） | 本方案 |
|------|-------------|-------------------|--------|
| 知识组织 | 文档段落 / 通用实体 / 中性叙述（可检索到案例与模式文本，但无攻击语义字段） | 无知识（模型+工具） | 字段化知识点：前提 / 探测 / 验证状态（§2） |
| 检索输入 | 自然语言问题 | 工具参数 | 场景上下文对象 |
| 输出 | 文本回答 | 工具调用结果 | 可执行工件（步骤/路径/骨架） |
| 知识演化 | 静态（随新文档演化，无实验反馈） | 静态 | 验证状态机 + 经验复利（实测回写） |
| 失败知识 | 无 | 无 | 一等公民（负知识页） |
| 多跳支撑 | 段落检索无多跳；图增强检索有**通用相关性**多跳（共现推断，无证据链） | 无 | 确定性关联事实（专家确认 + 证据）+ Agent 迭代组装路径 |
| 对 Agent 的增值 | 上下文 | 行动能力 | 行动能力 + 先验经验 + 记忆 |
| 失真对抗 | 无 | 无 | 实测结果覆盖 LLM 断言 |
| 目标支持 | 无目标概念 | 无 | 目标层级 + 降级链，支持动态调整（K4） |

## 11. hieraextract 过渡方案定位

### 11.1 过渡期的价值

在 llm_wiki + LightRAG 知识积累起来之前，hieraextract 提供两样启动资产：

1. **攻击面骨架**：`audit_bridge.AttackSurfaceBuilder` 的端点清单/服务依赖图/外部暴露 → 直接物化为 `surface/` 页种子（每端点一页，结构化字段进 frontmatter）——即 K2 的冷启动
2. **实体图种子**：L3/L4 实体（服务/组件）+ `entity_relations` → 导入 LightRAG（`service` 实体 + `reaches` 边）

### 11.2 退出路径

- 攻击面页由人工/后续验证持续修订，hieraextract 不再重跑后自动成为历史快照
- 实体图由 LightRAG 自身增量演化接管
- 退出后系统为双引擎形态，无对齐层、无三引擎维护成本

### 12.1 评估指标

- **场景命中率**：`kb_scenario` 返回 top-5 中命中「后来验证成功的场景」的比例
- **路径有效率**：`kb_path` 返回路径中被 Agent 采纳且走通的比例
- **POC 一次成功率**：`kb_poc` 骨架实例化后一次验证成功的比例
- **负知识复用率**：被拦截路径在后续场景构建中被正确排除的比例
- **复利曲线**：以上指标随验证次数（第 10/50/100 次）的变化趋势

## 13. 失真与安全考量

### 13.1 失真账本（两轮 LLM + 实测矫正）

| 失真源 | 形态 | 对策 |
|--------|------|------|
| llm_wiki 摄入 | 场景/叙述转述走样 | 页面溯源字段 + 实测状态覆盖 |
| LightRAG 实体提取 | 实体/关系错配（软边） | 路径每跳带依据 + `confidence`，Agent 决策时可见 |
| 无对齐层 | — | 零对齐错误（本方案收益） |
| **实测验证** | 环境事实 | **矫正器**：真实结果覆盖 LLM 断言（§5.4） |

### 13.2 安全

- POC 剧本、验证凭据、未修复漏洞细节 → `sensitive: true` 分级，检索按角色返回脱敏摘要
- 知识库服务仅绑定 127.0.0.1 + token 认证（与 llm_wiki 同模型）
- 验证动作本身受 Agent 侧权限约束，知识库只提供知识不执行攻击
- 审计日志：每次 `kb_record_verification` 与 POC 检索写入审计记录
